title: Sync Engine

`SyncEngine` orchestrates pushing queued local changes, pulling remote changes,
and resolving conflicts.

## Configuration

```ts
interface SyncPluginConfig {
  transport: SyncTransport        // required — how to communicate with server
  strategy?: ConflictStrategy     // "lww" (default), "client-wins", "server-wins", "custom"
  conflictResolver?: ConflictResolverFn
  autoSync?: boolean | {
    intervalMs?: number           // default 30000 (30s)
    debounceMs?: number           // default 500 (ms)
  }
  collections?: string[]          // restrict sync to specific collections
  pushBatchSize?: number          // default 50
  pullBatchSize?: number          // default 100
  retryMaxAttempts?: number       // default 10
}
```

If `autoSync` is enabled without an object, the default interval is 30 seconds
and the local-change debounce is 500 milliseconds. The default push and pull
batch sizes are 50 and 100 changes, respectively.

## The sync cycle

When `db.sync()` or `engine.sync()` is called, the engine runs:

```
sync()
  ├── push pending + failed changes (batch)
  │     ├── mark batch as "syncing"
  │     ├── transport.push(batch)
  │     ├── mark accepted as "committed"
  │     ├── resolve conflicts (apply strategy)
  │     └── mark errors as "failed"
  │
  ├── pull remote changes (paginated)
  │     ├── transport.pull({ cursor, batchSize })
  │     ├── apply each change locally
  │     └── update cursor for next pull
  │
  ├── clean up committed records
  ├── update counts & metadata
  └── emit "complete" event
```

### Push

Pending and retryable failed changes are sent in batches of
`pushBatchSize` (default 50). `retryMaxAttempts` (default 10) limits retries
per change; exhausted entries remain failed until manually retried. The
`collections` option filters both push and pull. Queue records move through
`pending`, `syncing`, `committed`, and `failed` states. Inspect and manage them
with the [sync utilities](/docs/sync/devtools).

### Pull

After push, the engine pulls remote changes starting from the last known
cursor. Pagination continues until the server indicates that no more changes
are available. A safety limit of 1,000 pages stops a pull if the server never
finishes pagination.

### Cleanup

Successfully committed records are removed from the queue.

## Auto-sync

When `autoSync` is enabled (recommended for most apps):

- **Interval sync**: runs `sync()` every `intervalMs` (default 30s)
- **Debounced sync**: local changes (from `onAfterCreate`/`onAfterUpdate`/`onAfterDelete`)
  trigger a debounced sync after `debounceMs` (default 500ms) of inactivity
- **Cross-tab sync**: `BroadcastChannel` change messages trigger a debounced
  sync in other tabs when that browser API is available
- **Online recovery**: when the browser comes back online, a sync is
  triggered immediately

## Online / offline detection

The engine listens to `window.online` and `window.offline` events:

- When going offline, `isConnected` becomes `false` — auto-sync timers
  still fire but transport calls will fail gracefully
- When coming back online, a sync is triggered immediately if auto-sync
  is enabled

## Retry backoff and circuit breaker

Automatic retries start after a one-second delay, double after each failure,
and cap at five minutes. Each delay uses 75%-125% jitter. After 50 consecutive
failed sync cycles, automatic retries stop scheduling; applications can
surface the error and request a manual sync.

## Sync events

```ts
interface SyncEvent {
  type: "sync"
  phase: "push" | "pull" | "conflict" | "complete" | "error"
  collection?: string
  changes?: number
  conflicts?: SyncConflict[]
  error?: Error
  progress?: SyncProgress
  timestamp: string
}
```

Listen via `db.onSync(callback)`:

```ts
db.onSync((event) => {
  switch (event.phase) {
    case "push":
      console.log(`Pushing ${event.changes} changes...`)
      break
    case "conflict":
      console.log(`${event.conflicts?.length ?? 0} conflicts to resolve`)
      break
    case "complete":
      console.log(`Sync done: ${event.progress?.pushed ?? 0} pushed, ${event.progress?.pulled ?? 0} pulled`)
      break
    case "error":
      console.error("Sync failed:", event.error)
      break
  }
})
```

## Transport errors

Transport errors update sync status and emit sync events; `db.sync()` does
not reject for ordinary transport failures. Check `db.syncStatus.lastError`
and listen to `db.onSync()` to surface failures in the UI. A transport's own
timeouts and reconnect behavior depend on its configuration.

## Metadata persistence

The engine persists two values in the adapter's metadata store:

| Key | Value |
|-----|-------|
| `sync:lastSyncAt` | ISO timestamp of the last successful sync |
| `sync:lastPullCursor` | Server-provided cursor for incremental pulls |

These survive page reloads, so the first pull after reload starts from
where the last sync left off.

## Status

```ts
interface SyncStatus {
  isSyncing: boolean
  isConnected: boolean
  lastSyncAt: string | null
  pendingChanges: number
  failedChanges: number
  lastError: string | null
}
```

Access via `db.syncStatus` or the `useSyncStatus()` React hook.
