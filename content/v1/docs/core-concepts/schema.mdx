A schema describes the collections, their fields, indexes, and relations.

## Preserve schema types

Use `defineSchema()` with `createDatabase()` to keep the schema's literal field
types and infer collection records:

```ts
import { createDatabase, defineSchema } from "ctrodb"

const schema = defineSchema({
  version: 1,
  collections: {
    todos: {
      fields: {
        title: { type: "string", required: true },
        done: { type: "boolean", default: false },
      },
    },
  },
})

const db = createDatabase({ schema })
const todos = db.collection("todos")
const todo = await todos.create({ title: "Typed" })
todo.title // string
todo.done  // boolean | undefined for records predating the default
```

`defineSchema()` preserves TypeScript literal types. Collection names that
match the schema are inferred, but the library also has a general string
overload, so undeclared names are not guaranteed to be rejected by TypeScript.
They are still checked at runtime when a schema is configured. Do not rely on
schema construction to validate every relation target or unknown field-type
string; cover those definitions in application tests.

## SchemaConfig

```ts
interface SchemaConfig {
  version: number       // must be a positive integer
  collections: Record<string, CollectionSchema>
}
```

`version{:ts}` must be a positive integer. `collections{:ts}` should include
the collections the application uses. IndexedDB uses the version to trigger
object-store and index upgrades.

## CollectionSchema

```ts
interface CollectionSchema {
  fields: Record<string, FieldDefinition>
  indexes?: IndexDefinition[]
  searchable?: string[]
  relations?: Record<string, RelationDefinition>
}
```

## FieldDefinition

| Option | Type | Description |
|--------|------|-------------|
| `type{:ts}` | `"string" \| "number" \| "boolean" \| "object" \| "array"{:ts}` | Data type |
| `required{:ts}` | `boolean{:ts}` | Throw if missing |
| `default{:ts}` | `unknown{:ts}` or `() => unknown` | Applied when omitted or `undefined`; `null` is not replaced |
| `min{:ts}` | `number{:ts}` | Minimum value (number fields) |
| `max{:ts}` | `number{:ts}` | Maximum value (number fields) |
| `maxLength{:ts}` | `number{:ts}` | Max string length |
| `items{:ts}` | `FieldDefinition{:ts}` | Schema for array items |
| `unique{:ts}` | `boolean{:ts}` | Enforce uniqueness via index |
| `validate{:ts}` | `"email" \| "url" \| RegExp{:ts}` | Built-in validators (string fields) |

### Array items

```ts
tags: {
  type: "array",
  items: { type: "string" }
}
```

### Default as function

```ts
createdAt: {
  type: "number",
  default: () => Date.now()
}
```

## Indexes

```ts
indexes: [
  { field: "email", unique: true },
  { field: "age" }
]
```

Indexes can accelerate matching a single field for `==`, `>`, `<`, `>=`, and
`<=`. The query planner chooses at most one suitable scalar index and applies
remaining predicates as filters; compound-index planning is not supported.
Unique indexes reject duplicate values at the storage layer.

## Relations

```ts
relations: {
  author: { type: "belongs_to", collection: "users", foreignKey: "userId" },
  posts: { type: "has_many", collection: "posts", foreignKey: "userId" },
  profile: { type: "has_one", collection: "profiles", foreignKey: "userId" },
}
```

Lazy relation getters and eager loading are built into the core — no plugin is
required. Relation declarations do not enforce foreign-key integrity, and
schema setup does not verify that relation targets exist.

## Schema methods

```ts
schema.getIndexes("todos")
schema.getRelations("posts")
schema.getSearchableFields("articles")
schema.applyDefaults("todos", data)
schema.validate("todos", data)
```

Core validation runs without the validation plugin and covers:

- Required fields
- Type checking (including array item types)
- String max length
- Number min/max
- Email and URL format and regular-expression patterns
- Unknown field rejection

The `validationPlugin()` adds extra built-in and custom rules; it is not
required for the schema rules above. Defaults are applied during writes, not
retroactively to existing records.

```ts
class SchemaError extends CtrodbError {}
class ValidationError extends CtrodbError {
  readonly field: string
  readonly collection: string
  readonly value: unknown
}
```
