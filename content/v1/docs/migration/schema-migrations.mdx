---
title: Schema Migrations
description: Evolving your database schema over time
---

As your application grows, you'll need to add fields, change validation rules, or restructure collections. ctrodb provides schema versioning and handles migration at the adapter level.

## Schema version

Each schema has a positive `version{:ts}` number. Increasing it triggers an
IndexedDB upgrade so newly declared stores and indexes can be created.

```ts
const schema = {
  version: 2,
  collections: {
    users: {
      fields: {
        name: { type: "string" },
        email: { type: "string", validate: "email" },
      },
    },
  },
}
```

## Adding new fields

New optional fields are safe to add — existing records simply won't have the field yet.

```ts
const schema = {
  version: 2,
  collections: {
    users: {
      fields: {
        name: { type: "string" },
        email: { type: "string", validate: "email" },
        avatar: { type: "string" }, // new field, optional by default
        role: { type: "string", default: "user" }, // new with default
      },
    },
  },
}
```

Defaults are applied at write time (when creating or updating records), not retroactively.

## Adding indexes

Indexes are created during IndexedDB upgrades. The memory adapter does not
provide native indexes, so its indexed scans still examine records:

```ts
const schema = {
  version: 3,
  collections: {
    users: {
      fields: { ... },
      indexes: [
        { field: "email", unique: true }, // new index
      ],
    },
  },
}
```

## Making fields required

Making an existing field `required: true` can make later writes to legacy
records fail validation until those records are backfilled. Backfill first,
then require the field in a later application release.

## Removing fields

ctrodb does not automatically remove data from existing records when you
remove a field from the schema, and removed object stores are not deleted.
Write and test an explicit data migration if cleanup is required.

## Manual data migration

ctrodb does not expose a user-defined schema-migration callback. For complex
migrations, connect using a schema that can still read the old records, then
run an application-owned migration script:

```ts
const db = new Database({ schema })
await db.connect()

const users = await db.collection("users").getAll()
for (const user of users) {
  if (user.role === undefined) {
    await user.update({ role: "user" })
  }
}
```

Track completion with application-owned migration state; avoid relying on the
private `_getAdapter()` method as a public migration API.

## Under the hood: IndexedDB versioning

When using the IndexedDB adapter, `schema.version` maps to the IndexedDB
database version. The adapter creates missing object stores and indexes during
`onupgradeneeded`; it does not transform existing records or remove stores
omitted from a later schema.

## Memory adapter

The Memory adapter does not persist between sessions, so versioning matters less. `getSchemaVersion(){:ts}` and `setSchemaVersion(){:ts}` work against in-memory metadata.
