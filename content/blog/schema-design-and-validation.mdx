ctrodb's schema system lets you define the shape, constraints, and defaults for
your data. Core validation runs on writes; `validationPlugin()` adds extra
built-in and custom rules. Good schema design is the foundation of a reliable
client-side application.

## Schema Structure

A schema is organized by version and collections:

```typescript
const schema = {
  version: 1,
  collections: {
    users: {
      fields: {
        name: { type: "string", required: true },
        email: { type: "string", required: true },
      },
      indexes: [{ field: "email", unique: true }],
    },
  },
}
```

For IndexedDB, `version` triggers object-store and index upgrades. ctrodb does
not provide a user data-migration callback, transform existing records, or
automatically delete stores removed from the schema.

## Field Types

ctrodb supports five field types:

```typescript
type FieldType = "string" | "number" | "boolean" | "object" | "array"
```

```typescript
const schema = {
  version: 1,
  collections: {
    products: {
      fields: {
        title: { type: "string" },        // string
        price: { type: "number" },         // number
        inStock: { type: "boolean" },      // boolean
        metadata: { type: "object" },      // object
        tags: {                             // array of strings
          type: "array",
          items: { type: "string" },
        },
      },
    },
  },
}
```

Type checking uses `typeof` (and `Array.isArray` for arrays). A record with a type mismatch will throw a `ValidationError` at write time.

## Validation Rules

### Required Fields

Mark a field as required to reject records without it:

```typescript
email: { type: "string", required: true }
```

Attempting to create a record without `email` throws:

```typescript
await users.create({ name: "Alice" })
// Throws: ValidationError: "email" is required in collection "users"
```

### Built-in Validators

The `validate` option supports email, URL, or regular expression validation:

```typescript
fields: {
  email: { type: "string", validate: "email" },
  website: { type: "string", validate: "url" },
  zipCode: { type: "string", validate: /^\d{5}(-\d{4})?$/ },
}
```

- `"email"` — Checks the format `<local>@<domain>.<tld>`
- `"url"` — Attempts to parse with `new URL(value)`
- `RegExp` — Tests the value against the pattern

### Custom Validation Functions

For custom logic beyond the built-in validators, use the [validation plugin](/docs/plugins/validation)
which supports `ValidationRule` objects with full field and collection context:

```typescript
import { validationPlugin } from "ctrodb"

const db = new Database({
  plugins: [validationPlugin([
    {
      name: "ageRange",
      validate(collection, field, value) {
        if (field === "age" && typeof value === "number" && (value < 0 || value > 150)) {
          return "Age must be between 0 and 150"
        }
        return null
      },
    },
  ])],
})
```

### Numeric Constraints

```typescript
fields: {
  price: { type: "number", min: 0 },
  quantity: { type: "number", min: 0, max: 999999 },
}
```

### String Length Constraints

```typescript
fields: {
  bio: { type: "string", maxLength: 500 },
  code: { type: "string", validate: /^\d{6}$/ },
}
```

## Default Values

Default values are applied automatically when a field is undefined:

```typescript
fields: {
  role: { type: "string", default: "user" },
  createdAt: {
    type: "string",
    default: () => new Date().toISOString(),
  },
  counter: { type: "number", default: 0 },
}
```

Function defaults (like the ISO date string above) are called for each new
record, giving you dynamic default values. Defaults replace omitted or
`undefined` fields, not explicit `null` values.

## Indexes

Indexes can accelerate a suitable single-field query and enforce uniqueness:

```typescript
indexes: [
  { field: "email", unique: true },
  { field: "category" },
  { field: "createdAt" },
]
```

The query planner can use at most one suitable scalar index for a query, then
filters remaining conditions. Compound-index planning is not supported.
Duplicate ID and unique-index failures currently reject with a plain `Error`.

## Searchable Fields

Declare string fields for tokenized matching:

```typescript
{ …,
  searchable: ["title", "body"],
}
```

`query().match()` uses these fields by default. It requires all remaining
whole-word tokens to match; `ftsPlugin()` accelerates the search but is not
required for correctness. `query().search(field, text)` is a separate
case-insensitive substring scan.

## Complete Example: User Profile Schema

```typescript
const schema = {
  version: 1,
  collections: {
    profiles: {
      fields: {
        username: {
          type: "string",
          required: true,
          validate: /^[a-zA-Z0-9_]{3,20}$/,
        },
        displayName: { type: "string", required: true, maxLength: 100 },
        email: { type: "string", required: true, validate: "email" },
        age: { type: "number", min: 13, max: 120 },
        bio: { type: "string", maxLength: 500, default: "" },
        role: { type: "string", default: "user" },
        isActive: { type: "boolean", default: true },
        tags: { type: "array", items: { type: "string" } },
        metadata: { type: "object" },
        createdAt: {
          type: "string",
          default: () => new Date().toISOString(),
        },
      },
      indexes: [
        { field: "username", unique: true },
        { field: "email", unique: true },
        { field: "role" },
      ],
    },
  },
}
```

## Error Handling

Validation errors carry useful metadata for debugging:

```typescript
import { ValidationError } from "ctrodb"

try {
  await users.create({ name: "Alice" })
} catch (err) {
  if (err instanceof ValidationError) {
    console.error(err.field)      // "email"
    console.error(err.collection) // "users"
    console.error(err.value)      // undefined
  }
}
```

Properties on `ValidationError`:
- `field` — The field that failed validation
- `collection` — The collection name
- `value` — The rejected value

## Schema-less Mode

When no schema is provided, ctrodb operates in schema-less mode:

```typescript
const db = new Database({ name: "scratch", adapter: "memory" })
await db.connect()

const items = db.collection("items")
await items.create({ name: "Widget", price: 9.99 }) // No validation
```

This is useful for prototyping, but for production applications, a well-defined schema catches bugs early.

## Schema Design Best Practices

1. **Define schemas early** — Even for simple apps, a schema catches type errors at the data layer instead of in your UI.
2. **Use required + default** — Required fields catch missing data, while defaults handle optional fields gracefully.
3. **Index fields you filter** — Add indexes for equality and range filters; sorting and substring searches are not accelerated by these field indexes.
4. **Set unique indexes** — For emails, usernames, slugs, or any field that must be unique.
5. **Validate at the boundary** — The schema is your data validation layer. Use it alongside UI validation for defense in depth.
6. **Version your schemas** — Increment `version` when IndexedDB stores or indexes need an upgrade; write an explicit application migration for existing data.

## Summary

ctrodb's schema system provides:

- Five field types with runtime type enforcement
- Built-in schema validators (email, URL, regex) plus extra built-in and custom rules via the validation plugin
- Numeric and string constraints (min, max, maxLength)
- Static and dynamic default values
- Index definitions for performance and uniqueness
- `ValidationError` with detailed metadata

A well-designed schema turns your client-side database from a simple key-value store into a robust, type-safe data layer.
