Full-text search is one of those features that feels simple until you implement it. This post explains how ctrodb's FTS plugin works under the hood.

## The naive approach

Without an index, searching means iterating every record and running `String.includes()`:

```ts
const results = allRecords.filter((r) =>
  r.title.toLowerCase().includes(query.toLowerCase())
)
```

This is simple, but scans every record and can become expensive as the dataset grows.

## Token-based indexing

ctrodb's FTS plugin takes a different approach. When a record is created or
updated, it extracts tokens from the schema's searchable fields and stores
postings that associate a collection, token, and document ID:

```
Token "database" -> [doc1, doc3, doc7]
Token "schema"   -> [doc1, doc4]
Token "react"    -> [doc2, doc5]
```

A search for "database schema" finds docs that have both tokens (AND logic).

## Tokenizer behavior

The tokenizer:

1. Lowercases the input
2. Splits on non-alphanumeric characters
3. Removes duplicates
4. Filters out stop words (a, an, the, and, ...)
5. Returns unique tokens

```ts
import { tokenize } from "ctrodb"

tokenize("Hello World! The database")
// ["hello", "world", "database"]
```

## Storage strategy

The postings live in the internal `_ctrodb_fts` store. Each posting represents
one collection-token-document association:

```ts
{
  id: "<composite posting key>",
  token: "database",
  collection: "articles",
  docId: "doc-1"
}
```

The store is maintained by the plugin; treat its internal record format as an
implementation detail. The built-in adapters support the index used to look up
postings by token.

## Query execution

When you call `.match("database schema", ["title", "body"])`:

1. The tokenizer splits the query into tokens: `["database", "schema"]`
2. The indexer looks up postings for each token
3. The document IDs are intersected so every remaining whole-word token must
   match. Without the FTS plugin, ctrodb computes the same matches by scanning
   records.

## Performance characteristics

- **Indexing**: adds or removes one posting per distinct searchable token
- **Search**: cost depends on the query tokens and matching postings; it is not
  constant-time and does not provide ranking
- **Storage**: grows with the number of distinct document-token pairs

## When to use it

The FTS plugin is useful when repeated tokenized searches justify the added
index storage and write work:

- Collections with searchable text fields (titles, descriptions, body content)
- Apps where every whole-word query term must match

It does not support fuzzy search, stemming, substring matching, or relevance
scoring. Use `.search()` for a case-insensitive substring scan; consider a
dedicated search service for fuzzy matching or ranking.
