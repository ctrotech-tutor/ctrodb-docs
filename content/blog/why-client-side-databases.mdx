## The latency problem

Users expect instant feedback. A local database avoids waiting for a network
round trip, although its reads and writes are still asynchronous operations.
Remote requests add variable latency, and that adds up.

## Offline is the default

Mobile users go through tunnels. Desktop users lose WiFi. Progressive web apps need to work without a connection. A client-side database means your app keeps running when the network drops, and syncs when it comes back.

## What ctrodb does differently

Existing client-side storage options each have trade-offs:

- **localStorage**: synchronous, blocking, strings only, with browser-managed
  storage limits
- **IndexedDB raw**: powerful but verbose, no schema, error-prone
- **SQLite (via WASM)**: heavy, complex, overkill for most apps
- **ctrodb**: schema-driven and reactive, with IndexedDB and memory adapters

ctrodb wraps IndexedDB and memory storage with a TypeScript API. Its automatic
adapter uses IndexedDB when available and otherwise uses volatile memory
storage. Define a schema for validation and indexes, and subscribe to changes
through its event system.

## The pattern that works

The most successful local-first apps follow a pattern:

1. **Local database** is the source of truth
2. **UI renders from local data** — reads avoid the network round trip
3. **Writes go to local DB first** — the UI need not wait for a network round trip
4. **Background sync** pushes to a server when connected

ctrodb provides the local database and also offers an optional sync plugin with
HTTP, WebSocket, and custom transports. You still choose and operate the server
and sync protocol for your application; synchronization starts only when
configured.

## Where to start

If you are building a new app, start with local persistence and add remote sync
when the product needs it. You can build and use local-first features without
configuring a sync server.
