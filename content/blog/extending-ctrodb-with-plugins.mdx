ctrodb's plugin system lets you hook into database and collection lifecycle
events and writes. The FTS and validation features use plugins; core relation
access and schema validation work without `relationsPlugin()` or
`validationPlugin()`. Those plugins are optional additions, not prerequisites
for the core APIs.

## Plugin Interface

Every plugin implements the `CtroDBPlugin` interface:

```typescript
interface CtroDBPlugin {
  name: string
  version?: string
  storeNames?: (string | PluginStoreConfig)[]
  onDatabaseInit?(db: unknown): void | Promise<void>
  onDatabaseDestroy?(db: unknown): void | Promise<void>
  onCollectionInit?(collection: unknown): void
  onBeforeCreate?(collection: string, data: unknown, context?: WriteContext): unknown
  onAfterCreate?(collection: string, record: unknown, context?: WriteContext): void
  onAfterCreateMany?(collection: string, records: unknown[], context?: WriteContext): void
  onBeforeUpdate?(collection: string, id: ID, changes: unknown, context?: WriteContext): unknown
  onAfterUpdate?(collection: string, id: ID, record: unknown, oldRecord?: unknown, context?: WriteContext): void
  onBeforeDelete?(collection: string, id: ID, context?: WriteContext): void
  onAfterDelete?(collection: string, id: ID, oldRecord?: unknown, context?: WriteContext): void
}
```

Hook callbacks may be asynchronous; ctrodb awaits them. The database and
collection callback parameters are typed as `unknown` in the public interface.
`onDatabaseDestroy()` runs when the database disconnects. The optional write
context identifies writes from the caller (`"local"`) or sync engine
(`"remote"`). `createMany()` calls `onAfterCreateMany()` once for a batch when
that hook is implemented.

### Hook Execution Order

For a create or update, ctrodb runs the before-hook before writing, then runs
after-hooks and emits change events after the write succeeds:

1. Apply defaults and validate schema data on create.
2. Run `onBeforeCreate` or `onBeforeUpdate` in plugin registration order.
3. Validate merged update data, then write through the adapter.
4. Run after-hooks and publish the change event.

Delete runs `onBeforeDelete`, deletes through the adapter, then runs
`onAfterDelete` and publishes its event. After-hook failures are logged and do
not roll back a write that is already durable.

### Data Modification

Only `onBeforeCreate` and `onBeforeUpdate` can modify data. If they return a
value, that value replaces the original data before it reaches the adapter.
Create data is schema-validated before `onBeforeCreate`; a plugin that changes
fields should preserve the schema constraints because the transformed create
data is not validated again. Update data is validated after its before-hooks.

```typescript
import type { CtroDBPlugin } from "ctrodb"

function asRecord(value: unknown): Record<string, unknown> | undefined {
  if (typeof value !== "object" || value === null || Array.isArray(value)) return
  return value as Record<string, unknown>
}

const timestampPlugin: CtroDBPlugin = {
  name: "timestamps",
  onBeforeCreate(_collection, data) {
    const record = asRecord(data)
    return record ? { ...record, createdAt: new Date().toISOString() } : data
  },
  onBeforeUpdate(_collection, _id, changes) {
    const record = asRecord(changes)
    return record ? { ...record, updatedAt: new Date().toISOString() } : changes
  },
}
```

## Example 1: Audit Log Plugin

Log every write operation with timestamps:

```typescript
import type { CtroDBPlugin } from "ctrodb"

const auditPlugin: CtroDBPlugin = {
  name: "audit",
  async onAfterCreate(collection, record) {
    const id = (record as { id?: unknown }).id
    console.log(`[AUDIT] Created ${collection}#${String(id)}`)
  },
  async onAfterUpdate(collection, id, record, oldRecord) {
    console.log(`[AUDIT] Updated ${collection}#${id}`, { from: oldRecord, to: record })
  },
  async onAfterDelete(collection, id, oldRecord) {
    console.log(`[AUDIT] Deleted ${collection}#${id}`)
  },
}
```

## Example 2: Slug Generator Plugin

Auto-generate URL-friendly slugs from titles:

```typescript
import { Database } from "ctrodb"
import type { CtroDBPlugin } from "ctrodb"

function asRecord(value: unknown): Record<string, unknown> | undefined {
  if (typeof value !== "object" || value === null || Array.isArray(value)) return
  return value as Record<string, unknown>
}

function slugPlugin(fields: { source: string; target: string }): CtroDBPlugin {
  return {
    name: "slug-generator",
    onBeforeCreate(collection, data) {
      const record = asRecord(data)
      const source = record?.[fields.source]
      if (record && typeof source === "string" && !record[fields.target]) {
        const slug = source
          .toLowerCase()
          .replace(/[^a-z0-9]+/g, "-")
          .replace(/^-+|-+$/g, "")
        return { ...record, [fields.target]: slug }
      }
      return data
    },
    onBeforeUpdate(collection, id, changes) {
      const record = asRecord(changes)
      const source = record?.[fields.source]
      if (record && typeof source === "string" && !record[fields.target]) {
        const slug = source
          .toLowerCase()
          .replace(/[^a-z0-9]+/g, "-")
          .replace(/^-+|-+$/g, "")
        return { ...record, [fields.target]: slug }
      }
      return changes
    },
  }
}

// Usage
const db = new Database({
  name: "blog",
  schema,
  plugins: [slugPlugin({ source: "title", target: "slug" })],
})
```

## Example 3: Prevent Hard Deletes

Block direct deletes and expose an application-level archive operation. Add the
`deletedAt` and `isDeleted` fields to the collection schema before using it.

```typescript
import { Database } from "ctrodb"
import type { CtroDBPlugin } from "ctrodb"
import type { ID } from "ctrodb"

function preventHardDeletePlugin(): CtroDBPlugin {
  return {
    name: "prevent-hard-delete",
    onBeforeDelete(collection, id) {
      throw new Error("Direct deletion not allowed. Use the archive method instead.")
    },
  }
}

async function archive(db: Database, collection: string, id: ID) {
  const col = db.collection(collection)
  await col.update(id, { deletedAt: new Date().toISOString(), isDeleted: true })
}
```

## Example 4: Validation Plugin with Custom Rules

The built-in validation plugin accepts custom rules:

```typescript
import { Database } from "ctrodb"
import { validationPlugin } from "ctrodb"
import type { ValidationRule } from "ctrodb"

const passwordRule: ValidationRule = {
  name: "strong-password",
  validate(collection, field, value) {
    if (field !== "password") return null
    if (typeof value !== "string") return "Password must be a string"
    if (value.length < 8) return "Password must be at least 8 characters"
    if (!/[A-Z]/.test(value)) return "Password must contain an uppercase letter"
    if (!/[a-z]/.test(value)) return "Password must contain a lowercase letter"
    if (!/[0-9]/.test(value)) return "Password must contain a number"
    return null
  },
}

const noPastDatesRule: ValidationRule = {
  name: "no-past-dates",
  validate(collection, field, value) {
    if (field !== "eventDate") return null
    if (typeof value !== "string") return null
    if (new Date(value) < new Date()) {
      return "Event date must be in the future"
    }
    return null
  },
}

const db = new Database({
  name: "secure-app",
  schema,
  plugins: [validationPlugin([passwordRule, noPastDatesRule])],
})
```

## Client-side encryption caveat

Base64 encoding is not encryption, and code shipped to a browser cannot keep a
static secret from the user who controls that browser. Do not treat a storage
plugin as a security boundary. If the application needs encryption at rest,
use a vetted cryptographic design and key-management flow appropriate to its
threat model; ctrodb does not provide key management.

## Plugin Architecture

### The Hook Runner

ctrodb's internal `runHook` utility manages plugin execution:

```typescript
async function runHook(
  plugins: CtroDBPlugin[],
  hookName: keyof CtroDBPlugin,
  ...args: unknown[]
): Promise<unknown>
```

It iterates all plugins in order. For mutation hooks (`onBeforeCreate`, `onBeforeUpdate`), the return value of each plugin is passed as the data argument to the next plugin, enabling a pipeline pattern.

### Plugin Registration Order

Plugins execute in the order they are listed in the `plugins` array:

```typescript
import { Database, ftsPlugin, validationPlugin } from "ctrodb"

const db = new Database({
  plugins: [
    validationPlugin(),   // Runs first
    ftsPlugin(),          // Runs second
    auditPlugin,          // Runs third
  ],
})
```

This matters when plugins modify data — earlier plugins see the original data, later plugins see the modified data.

## Testing Plugins

ctrodb's own tests use Vitest. Here's how you might test a custom plugin:

```typescript
import { describe, it, expect } from "vitest"
import { Database } from "ctrodb"

describe("slugPlugin", () => {
  it("generates slug from title on create", async () => {
    const db = new Database({
      adapter: "memory",
      plugins: [slugPlugin({ source: "title", target: "slug" })],
    })
    await db.connect()

    const posts = db.collection("posts")
    // Without schema, we can still test in schema-less mode
    const post = await posts.create({
      title: "Hello World! This Is a Post",
    })

    expect(post.slug).toBe("hello-world-this-is-a-post")
  })
})
```

## Summary

The ctrodb plugin system lets you:

- Hook into database init, collection init, and every CRUD operation
- Modify data before it's written (create/update)
- Observe operations after they complete
- Add custom validation rules with the validation plugin
- Build reusable behaviors (audit logging, slug generation, and archive workflows)
- Compose multiple plugins that pipeline data transformations

The FTS and validation features use the plugin API; relation access is built
into the core. Whether you need cross-cutting concerns like audit logging or
domain-specific logic like slug generation, plugins keep your code modular and
reusable.
